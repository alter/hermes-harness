## 3. Hermes: совместимость и реальное значение умолчаний

### 3.1. N4: релиз не принимает команду харнесса

Проверен список аргументов, используемый [run.sh](../run.sh):

```text
chat -Q --format stream-json --query-file - --accept-hooks
```

Результат исполнения штатных парсеров:

```text
345cd2b: exit 2, unrecognized arguments: --format stream-json
784d5c3f: parsed, output_format = stream-json
f4c83fe: parsed, output_format = stream-json
6182078: parsed, output_format = stream-json
```

В релизе отсутствие флага не компенсируется quiet-режимом: `-Q` не добавляет ожидаемый контроллером JSONL-контракт. Парсер, формат результата и чтение `session_id` должны проверяться совместно. Источники: [парсер релиза](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/hermes_cli/_parser.py), [парсер свежего SHA](https://github.com/NousResearch/hermes-agent/blob/6182078cb754f0d17ce83ade09d60e1250add111/hermes_cli/_parser.py), [stream JSON в совместимом снимке](https://github.com/NousResearch/hermes-agent/blob/f4c83fea4485030782c6e0f5680a2fa9196bd3b2/hermes_cli/stream_json.py).

**Поправка к первоначальному ревью:** успешные прошлые задачи исключают чистый указанный тег только при условии, что использовались именно эта команда и этот контроллер. Они не устанавливают происхождение исполняемого `hermes`. Позднее сообщение с SHA `784d5c3f` даёт конкретную исходную версию для анализа; её парсер проверен выше. Для воспроизводимой установки остаются важны путь к бинарнику, install directory и локальные изменения.

`hermes --version` — полезный первый шаг, но недостаточная универсальная аттестация. Реализация печатает upstream SHA для Git-установки через banner; предусмотрен fallback, который выводит только версию и дату. Даже SHA не отражает незакоммиченные патчи. Источник: [реализация вывода версии](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/hermes_cli/_startup_fast.py).

В будущий preflight нужны проверка поддерживаемого `stream-json`, фиксация идентичности установки и обработка отсутствующего/повреждённого result envelope. Простой поиск строки `--format` в help — только первый уровень. Старый эксперимент «релиз против upstream» возможен после адаптации формата; для неизменного харнесса сравнивать следует два совместимых закреплённых SHA.

### 3.2. Размышления: замечание по штатному режиму справедливо

На всех четырёх проверенных SHA, включая сообщённый серверный `784d5c3f`, обычный custom-маршрут не включает reasoning echo автоматически для Qwen. Функция политики дала одинаковые результаты:

```text
echo = false: {role: assistant, content: ANSWER}
echo = true:  {role: assistant, content: ANSWER, reasoning_content: REASONING}
```

Карточка Qwen устанавливает сохранение прошлых reasoning по умолчанию. Шаблон читает `message.reasoning_content`; при отсутствующем поле и включённом сохранении выводит пустой think-блок. Источники: [политика Hermes](https://github.com/NousResearch/hermes-agent/blob/6182078cb754f0d17ce83ade09d60e1250add111/agent/message_sanitization.py), [условие opt-in](https://github.com/NousResearch/hermes-agent/blob/6182078cb754f0d17ce83ade09d60e1250add111/agent/reasoning_params.py), [официальный шаблон](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/chat_template.jinja).

Воспроизведение: история `user → assistant(reasoning_content=OLD_REASONING_MARKER) → user`, затем рендер одного и того же шаблона с полем и без поля:

| Вход | Маркер reasoning в prompt | Пустой `<think>` у исторического assistant |
| --- | --- | --- |
| Поле удалено | Нет | Да |
| Поле сохранено | Да | Нет |

SHA-256 проверенного шаблона: `c3cf9e34abf4f9e36c2d72165aa9c132d3e2a725b6c2586aaa3a8af9d7a81041`. Загрузка через `main` и через закреплённую revision дала одинаковое содержимое.

Таким образом, `reasoning_echo: true` обоснован как кандидат на восстановление штатного режима модели. Сохранение `false` тоже требует измеримого обоснования. Но это не доказательство безусловного выигрыша `true`: более длинная история расходует контекст, может раньше вызвать сжатие и увеличивает стоимость повторного prefill при потере кэша.

**Что пока нельзя утверждать:** что именно сервер пользователя на каждом ходу теряет весь кэш или что включение echo обязательно ускорит задачи. При удалении ранее сгенерированных мыслей общий префикс может оборваться в месте удаления, но неизменившийся префикс до него остаётся; дальнейшее поведение зависит от шаблона, slots, checkpoints, истории запросов и других преобразований. Не всякий ход содержит reasoning. Установщик также сохраняет пользовательские параметры — отсутствие echo в шаблоне репозитория не доказывает его отсутствие на сервере.

Для старой сессии включение echo не гарантирует восстановления всей истории: поле могло сохраниться, отсутствовать, быть сжато или относиться к другому маршруту. Эксперимент следует начинать с сопоставимых новых сессий.

### 3.3. Новое уточнение: свежий Hermes меняет умолчание effort

В SHA `6182078` добавлен `unset_reasoning_default`. Когда для основного цикла Chat Completions reasoning-настройка отсутствует, Hermes запрашивает default активного provider profile. Custom profile возвращает `{enabled: true, effort: medium}`; затем значение может отправиться как `reasoning_effort`.

Это подтверждается новой функцией, её вызовом из `_reasoning_config_for_wire` в diff и реализацией `CustomProfile.default_reasoning_config`. Есть условия и исключения: другой transport, отсутствие default у профиля, модель, помеченная как не поддерживающая reasoning, отдельные Ollama-проверки и отказ маршрута от параметра. Источники: [reasoning_params](https://github.com/NousResearch/hermes-agent/blob/6182078cb754f0d17ce83ade09d60e1250add111/agent/reasoning_params.py), [custom profile](https://github.com/NousResearch/hermes-agent/blob/6182078cb754f0d17ce83ade09d60e1250add111/plugins/model-providers/custom/__init__.py), [изменение построения запроса](https://github.com/NousResearch/hermes-agent/compare/f4c83fea4485030782c6e0f5680a2fa9196bd3b2...6182078cb754f0d17ce83ade09d60e1250add111).

Следствие для экспериментов: одинаковый YAML без явно заданного effort не гарантирует одинаковую глубину reasoning после обновления Hermes. Следует фиксировать фактический API request. Новый default не следует объявлять ни дефектом, ни улучшением качества Qwen без измерений.

Официальный шаблон отдельно проверен со значениями `xhigh`, `medium`, `low`, `high`: первые три приняты, `high` вызывает `ValueError`. Общая способность CLI llama.cpp принять строку effort не гарантирует, что конкретный шаблон её поддерживает. `--reasoning-budget` и `reasoning_effort` — разные управляющие параметры.

## 5. Воспроизведения дефектов контроллера

В следующих опытах использовался настоящий код харнесса. Подставной Claude возвращал JSON envelope; стоимость в нём была искусственным числом `1.5`. Указанные ниже суммы не являются реальными расходами. Эксперименты доказывают поведение контроллера при заданных входах, а не вероятность таких ответов от настоящего Claude.

### 5.1. N1 — неизвестный вердикт не ограничивает повторные обращения

Вход: задача в `review`, `HH_PREGATE=0`, `HH_REVIEW_MAX=3`; Claude возвращает `structured_output.verdict="banana"`, обычную строку summary, evidence-массив и пустой unmet.

Получено:

```text
review round 1/2 → verdict: banana, usable: yes
review round 1/2 → verdict: banana, usable: yes
review round 1/2 → verdict: banana, usable: yes
reviewed: 3, settled: 0
```

После прогона: `status: review`, три вызова Claude, файла счётчика раундов нет, `ledger.tsv` не создан. Полная цепочка: [verdict.py](../verdict.py) проверяет только непустоту verdict; [review.sh](../review.sh) удаляет rounds-файл для usable-ответа; `case` не имеет default; очередь снова выбирает ту же задачу.

При обычном `HH_REVIEW_MAX=0` в этой ветке нет внутреннего условия завершения. `HH_REVIEW_MAX_ROUNDS=2` её не ограничивает. `--max-budget-usd 5` передаётся каждому вызову отдельно, а не всей очереди; его фактическая работа под сообщённой подпиской здесь не испытана. Под API-биллингом возможен денежный расход, под подпиской — исчерпание лимита. Универсальная формулировка: неограниченные повторные обращения без прогресса и без независимого общего бюджета.

Ограничение доказательства: JSON schema, передаваемая настоящему CLI, запрещает `banana`. Опыт намеренно моделирует нарушение границы интеграции. Он показывает отсутствие независимой защиты контроллера, но не то, что исправно работающий CLI обычно возвращает такое значение. Фраза «единственный путь неограниченного расхода» тоже сильнее проверки: исчерпывающий анализ всех аварийных путей не выполнен.

Исправление должно сочетать локальную валидацию, закрытую обработку неизвестного результата, конечный бюджет попыток и регистрацию **каждого** обращения до перехода статуса. Одной default-ветки недостаточно для восстановления уже потерянного учёта использования.

### 5.2. N2 — поддельный done действительно меняет очередь

Начальное состояние: `a` — todo/pending; `b` — todo/pending, depends `a`. Вызваны штатные команды:

```text
tasks.py --root <root> next                    → a
tasks.py --root <root> set <root>/a status done → exit 0
tasks.py --root <root> next                    → b
```

У `a` осталось `verify: pending`. Это воспроизведение не использует `--as reviewer`. `depends_met` проверяет только статус; `write_label` ограничивает имена полей, но не допустимые значения/переходы. [README](../README.md) о безвредности поддельного done противоречит текущему поведению. [status.sh](../status.sh) также считает такие задачи done и не выделяет несогласованность.

Важное дополнение: [selftest.sh](../selftest.sh) уже закрепляет этот сценарий как ожидаемый — после записи агентом done проверяет готовность зависимой задачи, при этом verify остаётся pending. Поэтому «исправить три строки» недостаточно как описание законченной работы. Нужны новые инварианты переходов, изменение противоречащих тестов и определённое правило для HUMAN/старых задач без результата ревью.

Минимальный инвариант программной задачи: зависимость открывается только после согласованного `done` и независимого `verify: passed`. Целевой инвариант дополнительно связывает приёмку с актуальным снимком результата. Проверка двух строк сама по себе не решает подмену файлов или откат содержимого после приёмки.

### 5.3. F1 — устаревший check представлен как проверка текущего дерева

Созданы два разных чистых коммита с разным содержимым `code.txt`. Настоящая функция fingerprint дала для обоих:

```text
da39a3ee5e6b4b0d3255bfef95601890afd80709
```

Это SHA-1 пустого потока: хэшируется разница с HEAD, а не идентичность содержимого. Затем сохранены `.check.out` с `OLD-OUTPUT-from-other-command`, `.check.rc=0` и старый fingerprint. Для нового HEAD задана другая команда `echo NEW-OUTPUT` и запущен полный reviewer.

При `HH_PREGATE=1` контроллер объявил reuse. При `HH_PREGATE=0` проверку вообще не выполнял, но старый output также попал в prompt. В обоих случаях prompt утверждал, что check уже выполнен на точно этом рабочем дереве, и задача после подставного passed перешла в done. Место ложной гарантии — [tasks.py](../tasks.py), построение review prompt; место безусловной передачи старого файла — [review.sh](../review.sh), `check_arg`.

Нужно единое свидетельство измерения: идентичность проверенного содержимого, команда, окружение и результат. Проверка свежести необходима при любом использовании output, включая отключённый pregate. Сам `passed` ревьюера не исправляет ложные исходные данные, сообщённые ему контроллером.

### 5.4. N3 — тот же код после коммита теряет пригодный замер

В полном сценарии `run.sh → review.sh` задачи хранились вне рабочего дерева, `HH_COMMIT=1`, `HH_MEASURE=1`, `HH_PREGATE=1`. Проверочная команда записывала свой cwd во внешний счётчик.

Результат:

```text
fingerprint после check, до commit: 83c8e961bae256d1a134d7309e508e6160c68a3b
fingerprint после commit:          da39a3ee5e6b4b0d3255bfef95601890afd80709
запуски check в рабочем дереве:    2
запуски check в baseline:          1
```

Контент кода между двумя рабочими проверками не менялся. Это ненужный повторный замер в стандартном успешном пути. Он не равен запуску baseline: baseline закономерно отдельный.

Формулировка «никогда» должна быть заменена условиями воспроизведения: изменённый код, созданный рабочий замер, успешный автокоммит, включённый pregate и заданная test command. Несостоявшийся коммит или иная ветка исполнения могут вести себя иначе. Исправление F1 должно одновременно запрещать ложные попадания и сохранять reuse при одинаковом проверяемом содержимом до/после коммита.

### 5.5. F2 — смешанный автокоммит

Временный проект содержал отслеживаемое дерево задач. До запуска worker в index добавлена посторонняя правка `tasks/a/labels.txt`, отдельно создан untracked `stranger.txt`; подставной Hermes изменил только `code.txt`.

В созданном настоящим `run.sh` коммите оказались:

```text
code.txt
stranger.txt
tasks/a/labels.txt
```

Исключение задачи из нового `git add` не очищает уже staged-содержимое, а `git commit` коммитит весь index. Широкий `git add` также подхватывает посторонний untracked. Утверждение F2 подтверждено полным сценарием.

Исправление не должно делать `reset` или удалять чужую работу. При общей копии нужен отказ от неоднозначного коммита; надёжнее отдельная рабочая область с установленным основанием и владением изменениями.

### 5.6. F3 — diff и измерение могут относиться к разному коду

Создан коммит A с `code.txt=SNAPSHOT_A`; в `.hermes-harness/review/a` записан `commit <SHA-A>`. Затем рабочий файл изменён на `LIVE_B`. Проверка — `cat code.txt`; запускается настоящий reviewer с pregate.

Полученный prompt одновременно содержал diff с `+SNAPSHOT_A` и check output `LIVE_B`. Подставной passed привёл к `done / verify: passed`.

Это детерминированное воспроизведение несогласованного состояния; конкурентные процессы для него не нужны. Для возникновения такого состояния в обычной работе достаточно последующих изменений общего дерева. Раздельные run/review locks и публикация `status: review` до автокоммита создают дополнительные окна, подтверждённые чтением кода, но отдельный конкурентный stress test не проводился.

Общая блокировка снижает риск одновременного изменения; она не делает корректным ревью старого commit A по уже изменённому дереву B. Проверяющий процесс должен читать и тестировать зафиксированный снимок, к которому относится diff.

### 5.7. F4 — структура и согласованность результата не проверены локально

Прямые вызовы настоящего `verdict.py`:

| Вход | Полученный результат |
| --- | --- |
| passed, `unmet=["requirement not met"]`, `evidence=[{"claim":""}]` | exit 0, `passed 0 yes` |
| passed, evidence только с `claim="read source"`, задана test command | exit 0, `passed 0 yes` |
| passed, `summary=42` | exit 1, `AttributeError` на `.strip()` |

Первый опыт подтверждает противоречивый passed. Второй показывает, что наличие test command само по себе не требует подтверждённого её выполнения: проверка отказов срабатывает только при соответствующей записи permission denial. Третий — дополнительный аварийный путь: неожиданный тип не оформляется как unusable-review, а роняет парсер.

JSON schema на стороне CLI полезна, но не заменяет проверку объекта на собственной границе. Сначала нужны строгие типы и enum, затем согласованность verdict/unmet/evidence. Для обязательных проверок основанием должны служить идентификаторы результатов доверенного runner, а не поиск подстроки команды в утверждении модели.

### 5.8. F5, F6 и N5 — границы доступа

F5 подтверждается архитектурой: выбор роли `--as reviewer` — аргумент CLI, не удостоверение полномочий. Текстовые hooks не отделяют права процесса от прав владельца файлов. Отдельный worktree полезен для порядка работы, но сам по себе не закрывает остальные доступные пути и общую Git metadata.

F6 подтверждён генерацией `Bash(python3:*)` из test command, начинающейся с `python3`. Официальные правила Claude Code описывают `:*` как wildcard по остатку команды, а `dontAsk` сохраняет предварительно разрешённые действия. Это шире одной тестовой команды. Источник: [официальная документация permissions](https://code.claude.com/docs/en/permissions).

Для N5 выполнены непосредственно во временном каталоге:

```bash
sed -n 'w sed-created.txt' code.txt
git diff --output=diff-created.txt
```

Первая команда создала файл 9 байт, вторая — 121 байт. Они начинаются с префиксов, включённых в allowlist. **Доказана запись этими командами; обход permission engine установленного Claude Code не доказан.** У CLI есть отдельная обработка shell-синтаксиса и дополнительные ограничения. Реальный вызов модели для испытания этой гипотезы не выполнялся.

Целевое исправление — контролируемые проверки и среда, в которой ревьюер не может менять исходники снимка и состояние приёмки. Тестам могут потребоваться writable tmp/build/cache-каталоги. Нужно защищать и контроллер от исполняемых тестов проекта: код, запущенный тестовой командой, тоже не должен иметь возможность переписать доверенные manifests/вердикты.

### 5.9. F7 — одной точки в форме достаточно для передачи на ревью

Подставной Hermes ничего не изменил в коде, добавил единственный символ `.` к заготовке `NOTES.md` и завершился с exit 0. Настоящий `run.sh` передал задачу в review. Проверка формы сводится к отличию от scaffold; полноту доказательств контроллер не валидирует.

Этот опыт обходит модель и hook lifecycle намеренно: он проверяет, есть ли обязательная валидация на последней границе перед расходованием Claude. Её нет. Для задач без изменений кода тоже должен существовать явный допустимый результат с содержательными доказательствами, а не требование обязательно редактировать файл.

### 5.10. F8 — подтверждение по коду, без искусственного многосуточного прогона

Подтверждены перезапись worker `.ndjson` и `.err`, сохранение только одного previous reviewer JSON, baseline-key из SHA и строки команды без идентичности среды, а также неуникальное преобразование пути задачи `/ → -`. Например, `a-b/c` и `a/b-c` получают один slug.

Это разные проблемы, и общий ответ «улучшить логи» слишком расплывчат. Нужны устойчивый task ID, отдельный attempt ID, история каждой попытки и учёт расходов независимо от вердикта. Для baseline требуется определённая политика изменения окружения и сроков переиспользования. Сама фиксация версии Python не описывает весь набор зависимостей и внешних данных.

### 5.11. N6 — недоступность ревьюера блокирует все задачи

Дополнение из обновлённого ревью воспроизведено независимо. Созданы три задачи в review, подставной Claude на каждый вызов возвращает валидный JSON-объект с `is_error=true`, текстом о лимите использования, без structured verdict и с exit 1. Запуск ограничен шестью обращениями для безопасности эксперимента.

```text
a: round 1/2 → unusable; round 2/2 → blocked
b: round 1/2 → unusable; round 2/2 → blocked
c: round 1/2 → unusable; round 2/2 → blocked
reviewed: 6, settled: 0
```

Все три задачи сохранили `verify: pending`, но получили `status: blocked`; ledger записал причины `unusable review` и `2 unusable reviews`. Между обращениями нет паузы, очередь последовательно расходуется как список задач, которые якобы невозможно оценить. Артефакты этого отдельного опыта: `/private/var/folders/n6/lh59htn97s32m6r1xszt0x0r0000gn/T/hh-third-report-ivdcgaw_/N6`.

Это подтверждает обработку **смоделированного** отказа провайдера. Реальный envelope установленного Claude при исчерпании подписки по-прежнему не получен. Сходный путь возможен при ошибке аутентификации или сети; неверные типы envelope могут вместо этого вызвать аварийный выход, как в F4. Поэтому утверждение «форма ответа никогда не важна» слишком широкое.

Нужны отдельные исходы: содержательный verdict; нарушение протокола ответа; недоступность сервиса/лимит. Последнее не должно увеличивать число неудачных содержательных ревью или блокировать все задачи. Контроллер должен сохранить review, записать причину и остановить очередь либо использовать ограниченные повторения с паузами. Отсутствие `structured_output` само по себе ещё не доказывает временный rate limit: неизвестную ошибку следует сохранять и ограничивать, не зацикливая автоматически.

### 5.12. Подписка и расчётный USD

Режим подписки сообщён в обновлённом ревью; credentials и биллинг аккаунта этой проверкой не обследовались. Официальная документация подтверждает, что для Pro/Max session cost не является суммой к оплате: долларовая оценка вычисляется по токенам, а доступность подписки отражается отдельными показателями использования. Источник: [учёт использования Claude Code](https://code.claude.com/docs/en/costs).

Для описанного режима основными метриками должны стать вызовы, ходы и токены ревьюера на корректно принятую задачу, число событий исчерпания лимита и время простоя. `total_cost_usd` можно хранить как расчётную оценку рядом с указанием режима, но нельзя подписывать как фактически потраченные деньги или вычислять по ней остаток подписки. Если включены дополнительные оплачиваемые credits либо используется API-ключ, денежный учёт ведётся отдельно; такие настройки здесь не установлены.

Сравнение по числу вызовов тоже не вполне достаточно: один большой review и один короткий расходуют разный ресурс. Нужны доступные токенные метрики и реальные события лимита. Действие `--max-budget-usd` под подпиской не доказано ни наличием флага, ни подставным JSON; до проверки его нельзя считать гарантией защиты лимита.

## 7. Уточнённая первая партия исправлений

Цель остаётся исходной: Qwen выполняет заранее подготовленные программистские задачи, Claude независимо проверяет результат, а контроллер не позволяет подменить фактическую приёмку отчётом модели. Главные метрики — использование Claude на корректно принятую задачу и ложные приёмки; для сообщённой подписки это вызовы/ходы/токены, события лимита и простой, а не расчётный USD. ## 8. Серверная проверка и корректный эксперимент

### 8.1. Какие сведения действительно отсутствуют

Уже сообщены Hermes `784d5c3f`, llama.cpp `5b59b83`, имя/размер/checksum основного GGUF и драйвер 616.56; upstream SHA и каталог сверены. Не следует повторно просить их как неизвестные. Не хватает идентичности **исполняемой** установки харнесса, локальных изменений Hermes, версии Claude Code и реального limit-envelope, командной строки сервера, эффективной конфигурации профиля, фактического chat template, MTP-загрузки и наблюдений по запросам/кэшу.

Это не повторный запрос уже записанных названий версий. Документы описывают целевой стек, но несовместимость CLI и изменчивые defaults показывают, что они не являются снимком исполняемой установки.

Для воспроизводимого паспорта установки подходят следующие команды; повторять уже сохранённый вывод версии без изменения установки не требуется:

```bash
command -v hermes
hermes --version
hermes chat --help
command -v claude
claude --version
llama-server --version
nvidia-smi --query-gpu=name,driver_version,memory.total --format=csv
```

Затем в фактическом install directory Hermes: `git rev-parse HEAD` и `git status --short`. В контейнерной или пакетной установке дополнительно нужен идентификатор образа/пакета, а при отсутствии Git SHA не следует выдумывать его из номера версии. URL `/props`, имя профиля и путь к GGUF нужно брать из действующего запуска. Одного вывода `hermes --version` для всего этого недостаточно.

### 8.2. Порядок сравнения настроек

1. Сначала добиться проверяемой приёмки и наблюдаемого runtime. Иначе улучшение числа done может означать улучшение ложной отчётности.
2. Зафиксировать один SHA Hermes, одну модель и шаблон; явно определить effort. Учесть новый custom-default medium, если установлен соответствующий код.
3. Сравнить replay reasoning с сохранением и без него на одинаковом наборе задач. Режим с сохранением — эталон соответствия официальному шаблону; режим без него должен обосновать свою пользу.
4. Изменять compression cap отдельно, после замера фактического контекста и output reservation. Порог не обосновывать снятым диагнозом драйвера.
5. Проверять MTP, checkpoints, KV-типы и другие serving-параметры отдельными сериями. Фиксировать cold/warm условия и одинаковую политику cache reset.
6. Сравнивать версии Hermes только при совместимом контракте CLI и известных эффективных параметрах. Иначе одновременно меняются harness behavior и режим модели.

Измерять: правильность по независимому ревью; ложные passed и пропуски требований; вызовы/ходы/токены всех попыток, а не только успешной; события исчерпания подписки и простой; расчётный USD отдельно от реальных списаний, если они есть; число возвратов; полное время до приёмки; prompt/decode отдельно; сохранённый префикс и повторный prefill; длину reasoning, compaction events и потерю контекста. Для стохастической генерации нужны повторения — единичное прохождение не доказывает превосходство настройки.

## 9. Границы доказанного и сохранность исходных документов
