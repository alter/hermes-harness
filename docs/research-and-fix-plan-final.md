## 1. Итог

Ответ прав во всех восьми пунктах своей сводной таблицы. В шести из них неправ был я, причём в двух — не в формулировке, а в решении, которое я отдал бы исполнителю:

- **правило T03 «на задаче B ревьюер ответил → значит, дело в задаче A» неверно.** Контрпример ответа корректен, я воспроизвёл его на своей же пробной реализации: три общих сбоя, восстановление, ответ по B — и исправная A заблокирована с ложной причиной. Я проверял это правило двумя сценариями (вечный сбой и «ядовитая» задача) и не проверил третий — сбой, который кончился. Правило из задач убрано целиком;
- **правило T02 «нестроковые элементы `unmet` отбросить» превращало противоречивый `passed` в чистый.** `unmet: [42]` после моей «нормализации» становилось `unmet: []`. Это тот же класс ошибки, что T02 должна была закрыть.

Оба исправления переписаны, реализованы в копии репозитория по тексту задач и прогнаны, включая контрпример ответа (§3).

Разногласий по фактам не осталось. Осталось одно расхождение в оценке — не по существу (§2, п. 7).

## 3. Проверка переписанных T02 и T03

Реализованы в чистой копии репозитория строго по тексту задач (код из блоков файла подставлялся программно, а не переписывался руками), затем `./selftest.sh`.

```text
passed 181, failed 2
  FAIL  a run that produced nothing is refused      got: none 0 infra
  FAIL  the reason names the exit code
```

Красные — ровно те две старые проверки, которые T03 (шаги 1–2) велит изменить поимённо. Все новые сценарии зелёные:

| Сценарий | Что проверяет | Результат |
| --- | --- | --- |
| `p-banana` | неизвестный вердикт: два раунда, затем `blocked` | `reviewed: 2`, `blocked` |
| `p-string-evidence` | `evidence` строкой | задача осталась `review` / `pending` |
| `p-infra` | сбой на каждом вызове, четыре запуска | никто не заблокирован; 4 вызова — 4 строки в `calls.tsv`, расчётная стоимость сбойного вызова сохранена |
| `p-recover` — **контрпример ответа** | три сбоя независимо от задачи, затем восстановление | A не обвинена и не заблокирована, B отревьюена; при следующей попытке A проходит; 5 вызовов — 5 записей; `status.sh` показывает `reviewer calls: 5` |
| `p-poison` | вызов падает только на A | очередь дошла до B; A отложена, осталась в `review`, видна в `status.sh` |

Двенадцать входов с нарушенной структурой на пробном `verdict.py`:

```text
baseline (must be yes)   passed 0 yes      unmet [42]                passed 0 no
summary 42               passed 0 no       unmet missing             passed 0 no
evidence string          passed 0 no       tool_input 42             passed 1 no
claim 42                 passed 0 no       structured_output string  none 0 no
command 42               passed 0 no       envelope list             none 0 infra
banana                   banana 0 no       not json                  none 0 infra
```

Ни одного исключения, ни одной ложной приёмки, корректный ответ по-прежнему принимается.

Граница этой проверки: пробная реализация — моя, исполнитель напишет свою. Прогон доказывает, что задачи выполнимы, сценарии в них исполнимы и ловят то, что должны, — и больше ничего.

## 6. Урок этой итерации

Оба моих ошибочных решения прошли мою же проверку: я прогонял их в копии репозитория, и сценарии были зелёными. Зелёными они были потому, что я написал сценарии под то поведение, которое задумал, а не под то, которое может случиться. Контрпример нашёл тот, кто не писал решение. Это ровно то свойство, ради которого существует весь харнесс, и оно относится к задачам так же, как к коду: `fix-tasks.md` после исполнения принимать по выводу `./selftest.sh` и `git diff --stat`, а задачи T04–T13 перед исполнением стоит отдать тому же проверяющему, что разобрал T02 и T03.
