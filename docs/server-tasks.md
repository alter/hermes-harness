# Часть 2. Сервер: задачи, которые выполняются только там, где стоят RTX 5090, llama-server, Hermes и Claude Code

Первая часть — код харнесса, который пишется и проверяется на любой машине, — в [fix-tasks.md](fix-tasks.md). Основание обеих частей — [итоговая проверка](research-and-fix-plan-final.md).

Здесь нет ни одной правки кода харнесса. Здесь то, чего с другой машины не узнать и не сделать: что на сервере на самом деле установлено и запущено, как ведёт себя модель и сервер под нагрузкой, как отвечает настоящий Claude Code, выкатка исправленного харнесса и сравнение настроек.

## 0. Правила для того, кто работает на сервере

1. **Роли.** Задачи с пометкой «только чтение» может выполнять агент. Всё, что меняет установку, останавливает сервер или тратит лимит подписки, выполняет человек или агент с прямым разрешением человека на именно это действие.
2. **Нужен вывод команд, а не выводы.** Результат каждой задачи — файл с командой и тем, что она напечатала, дословно. Советы, оценки и предложения «заодно обновить» не нужны и в файл не пишутся. Что делать с фактами, решается не на сервере.
3. **Ничего не обновлять.** Hermes закреплён на upstream `784d5c3f9c2cb77698d8a9d2e72b1d106a38ea88`, llama.cpp — на `5b59b83f4e2101ea173d4f853a0522d9971f48c6`, модель — `Qwen3.8-27B-UD-Q6_K.gguf`, sha256 `c9c206812fbe4ac7b76a729e25928b63f2ae89d37f69da7a71c20aec763cd436`. Сообщение `hermes` «N commits behind — run hermes update» основанием для обновления не является. Более новый Hermes (проверено на `6182078`) при незаданном уровне размышлений сам отправляет серверу `reasoning_effort: medium` — обновление может молча изменить режим модели.
4. **Команду `hermes-agent` не запускать вообще.** Это отдельный вход upstream (`run_agent:main`), который без запроса начинает демонстрационный диалог с моделью и веб-поиском. Версию даёт только `hermes --version`.
5. **Не мешать идущей работе.** Пока существует `<проект>/.hermes-harness/run.lock` или `review.lock` с живым pid, на `:8080` ничего не слать и сервер не трогать. Исключение одно — `GET /props`: он модель не вызывает. У сервера одна ячейка (`--parallel 1`); посторонний запрос занимает её, и вернётся ли потом кэш идущей задачи, зависит от host-кэша (`--cache-ram`) и заранее неизвестно.
6. **Старое остаётся на месте** до приёмки нового: прежняя копия `~/.hermes/harness`, прежний `config.yaml`. `install.sh` делает резервную копию сам и печатает команду отката — сохрани её.
7. **Лимит подписки нарочно не выжигать.** Задачи, которым нужен настоящий вызов Claude, помечены, и в каждой сказано, сколько вызовов она стоит.

## R1. Факты об установке

**Только чтение.** Ничего не перезапускать, не устанавливать, не обновлять.

**Зачем.** Документы репозитория описывают, каким стек задуман. Уже выяснилось, что задуманное и установленное расходятся: README называл версию Hermes, на которой харнесс не запускается. Версии Hermes, llama.cpp, имя и sha256 модели, версия драйвера (616.56) уже известны — их заново не собирать.

**Что собрать** — команда и её вывод, дословно:

1. Команда, которой запущен `llama-server`: `ps -o args= -C llama-server`, либо текст systemd-юнита или скрипта запуска.
2. Из журнала сервера: строки при старте со словами `mtp`, `draft`, `speculative`; строки `cache_reuse is not supported`, если есть; любая строка с долей принятых черновиков после длинного ответа; строки про checkpoint при обработке запроса; строка о размере KV-кэша.
3. Шаблон и окно:

```bash
curl -s http://127.0.0.1:8080/props | python3 -c "
import json,sys,hashlib
d=json.load(sys.stdin); t=d.get('chat_template','')
print('n_ctx', d['default_generation_settings'].get('n_ctx'))
print('template chars', len(t), 'sha256', hashlib.sha256(t.encode()).hexdigest())
for word in ('preserve_thinking','reasoning_effort','xhigh'): print(word, word in t)"
```

   Для сравнения: sha256 официального шаблона `Qwen/Qwen3.8-27B` — `c3cf9e34abf4f9e36c2d72165aa9c132d3e2a725b6c2586aaa3a8af9d7a81041`. Несовпадение — не ошибка, а факт, его надо записать.
4. Есть ли в GGUF встроенная MTP-голова: число тензоров со словом `nextn` в имени. Например: `python3 <каталог llama.cpp>/gguf-py/gguf/scripts/gguf_dump.py <файл> | grep -c nextn`. Отдельно — есть ли тензор `blk.64.nextn.eh_proj.weight`.
5. Слитая конфигурация Hermes: `grep -n 'reasoning\|threshold\|context_length\|max_tokens\|default:' ~/.hermes/config.yaml`. Нужны `reasoning_echo`, `reasoning_effort`, `reasoning_overrides`, `compression.threshold`, `threshold_tokens`.
6. Что на самом деле исполняется: `diff -rq <клон hermes-harness> ~/.hermes/harness | head -40` и `git -C <клон> log --oneline -1`.
7. `command -v hermes`; в каталоге установки Hermes — `git rev-parse HEAD` и `git status --short | head -40` (есть ли незакоммиченные правки).
8. `command -v claude` и `claude --version`.
9. `nvidia-smi --query-gpu=name,driver_version,memory.total,memory.used --format=csv`.

**Результат.** Файл `docs/server-facts.md` в репозитории: девять разделов, в каждом команда и её вывод. Без пересказа и без рекомендаций. Закоммитить и отправить в `origin/main` — его ждёт первая часть.

## R2. Числа о сервинге

**Не меняет установку, но шлёт запросы на `:8080`.** Выполнять, только когда нет живых `run.lock` и `review.lock`.

**Зачем.** В `model-serving.md` приёмка сервера требовала предупреждения по номеру драйвера и отката на 580.x при замедлении после ~70k токенов. Этот диагноз отозван автором исходного сообщения (llama.cpp issue 27623): метрика делила токены на полное время запроса вместе с prefill, и обрыв не воспроизвёлся ни на одном драйвере. Правило по номеру драйвера снято. Остаётся то, что имеет силу: собственный замер на этой карте.

**Что измерить.** Все числа — из таймингов журнала сервера (`prompt eval time`, `eval time`), а не делением числа токенов на время запроса.

1. Скорость обработки запроса (prefill) и скорость декодирования при длине контекста около 30k, 60k и 90k токенов. Шесть чисел. Запрос — любой текст нужной длины и `max_tokens` порядка 200.
2. Декодирование на ответе длиннее 500 токенов с `--spec-type draft-mtp` и без него — два запуска сервера на **другом порту** (например 8081), рабочий на 8080 не трогать. Доля принятых черновиков из журнала.
3. Занятая память по `nvidia-smi` под нагрузкой при `-c 131072`.
4. Поведение кэша между двумя ходами агента: два запроса подряд, второй продолжает первый. Из журнала — сколько токенов взято из кэша, сколько обработано заново, была ли восстановлена контрольная точка. Затем то же, но между ними вставить посторонний короткий запрос: вернулся ли кэш первого разговора. Это отвечает на вопрос, чего стоит посторонний запрос при `--parallel 1`.
5. Проверка `tool_calls` из раздела 4 `model-serving.md`: `tool_calls: True`, `reasoning separated: True`.

**Результат.** Файл `docs/serving-report.md`: точная команда запуска, числа из пунктов 1–5 с выдержками журнала, версия драйвера как часть описания окружения — без выводов по её номеру.

## R3. Как на самом деле отвечает Claude Code

**Стоит 3 вызова подписки. Выполняет человек.** Видеокарта и модель не нужны.

**Зачем.** Все проверки первой части идут с подставным `claude`. Четыре вещи о настоящем остаются неизвестными, и от каждой зависит решение:

| Неизвестное | От него зависит |
| --- | --- |
| Соблюдает ли CLI JSON-схему так, что ответ вне её невозможен | насколько вероятны входы, от которых защищает T02 |
| Пропускает ли движок разрешений `git diff --output=…` и `sed -n 'w …'` | был ли путь записи у ревьюера до T11 реальным |
| Действует ли `--max-budget-usd` под подпиской | можно ли считать его потолком одного ревью |
| Как выглядит ответ при исчерпании лимита | верно ли T03 отличает сбой вызова от негодного ревью |

**Что сделать.** В пустом временном каталоге с `git init` и одним файлом, теми же флагами, что в `review.sh` (`--permission-mode dontAsk --tools "Bash,Read,Grep,Glob" --allowedTools … --output-format json --json-schema …`), сохраняя весь JSON-конверт и код выхода каждого вызова:

1. Один обычный вызов с коротким заданием и схемой из `review.sh`. Сохранить конверт: какие в нём поля (`structured_output`, `total_cost_usd`, `num_turns`, `usage`, `subtype`, `permission_denials`).
2. Один вызов со старым списком разрешений (`Bash(git diff:*)`, `Bash(sed -n:*)`) и просьбой выполнить `git diff --output=probe1.txt` и `sed -n 'w probe2.txt' <файл>`. Сохранить конверт; записать, появились ли файлы и что попало в `permission_denials`.
3. Один вызов с `--max-budget-usd 0.01` и заданием, которое заведомо дороже. Сохранить конверт и код выхода: остановился ли вызов, какой `subtype`.
4. Не вызывать специально: при первом настоящем исчерпании лимита сохранить без изменений `<проект>/.hermes-harness/logs/<задача>.review.json`, `.review.err` и код выхода из вывода `review.sh`.

**Результат.** Файл `docs/claude-facts.md`: версия `claude`, четыре раздела с конвертами дословно. Пункт 4 дописывается, когда случится.

## R4. Выкатить исправленный харнесс

**Меняет установку. Выполняет человек.**

**Условия начала.** В `origin/main` лежат закрытые T00–T09 первой части; есть `docs/server-facts.md` из R1. Нынешний HEAD (`6af3c16`) **раньше исправлений на сервер не нести**: относительно установленной там версии он добавляет ложное переиспользование замера проверки проекта.

**Шаги.**

1. Дождаться, пока нет живых `run.lock` и `review.lock`.
2. В клоне: `git pull`, затем `./selftest.sh | tail -1` → `failed 0`.
3. **Ворота для двух строк `config.yaml`.** Перед `install.sh` сверить с `server-facts.md`:

| Строка в `config.yaml` репозитория | Оставить, если | Иначе |
| --- | --- | --- |
| `model.reasoning_echo: true` (T13) | в шаблоне на сервере есть `preserve_thinking` (R1, п. 3) | удалить строку из `config.yaml` клона перед установкой и записать почему |
| `agent.reasoning_effort: xhigh` (T14) | в команде запуска нет `--reasoning-effort` (п. 1); в шаблоне есть `reasoning_effort` и `xhigh` (п. 3); в слитой конфигурации уровень не задан или `xhigh` (п. 5) | то же |

   Причина строгости второй строки: шаблон Qwen3.8 на неизвестное значение уровня бросает исключение, и тогда падает каждый запрос.
4. `./install.sh`; сохранить напечатанную команду отката. Затем `./selftest.sh ~/.hermes | tail -1` → `failed 0`, и `hermes hooks doctor` без предупреждений.
5. `diff -rq <клон> ~/.hermes/harness` — различий в скриптах нет.
6. Один прогон одной задачи глазами: `HH_MAX_TASKS=1` для `run.sh`, затем `HH_REVIEW_ONLY=<задача>` для `review.sh`. Проверить: в `.hermes-harness/calls.tsv` появилась строка; `status.sh` печатает `reviewer calls`; запись в `.hermes-harness/review/<задача>` начинается с `commit`.

**Результат.** В `docs/server-facts.md` дописан раздел «после выкатки»: вывод шагов 2, 4, 5 и 6, решение по двум строкам из шага 3.

## R5. `reasoning_echo`: включить по измерению

**Меняет одну настройку. После R4.**

**Зачем.** Штатный режим Qwen3.8 — сохранять размышления всех прошлых ходов; Hermes по умолчанию их вырезает, и шаблон рендерит на их месте пустой блок. Обосновывать измерением нужно отказ от штатного режима, а не возврат к нему. Но цена у возврата есть: производитель мерил модель на окне 256k, здесь окно 131k и сжатие истории на 98 304 токенах; с сохранёнными мыслями история растёт быстрее, а сжимает её та же локальная модель — медленно и с потерей деталей.

**Шаги.**

1. Выбрать одну реальную задачу средней длины. Назвать критерий отката **до** прогона и записать его: например, «с `true` задача не дошла до `review` из-за сжатий» или «вердикт ревьюера хуже».
2. Два прогона в **новых** сессиях (не resume): `model.reasoning_echo: false` и `true`. Остальное одинаково, включая состояние кэша сервера на старте (перезапуск `llama-server` перед каждым).
3. Для каждого записать: число сжатий контекста, время до `review`, вердикт шлюза, вердикт ревьюера и его раздел «Not met», число `finish_reason: length` в `ndjson`.
4. Оставить `true`, если критерий отката не сработал; иначе `false`. Один прогон на плечо — это проверка на грубую поломку, а не доказательство выигрыша; так и записать.

**Результат.** Раздел в `docs/serving-report.md` с критерием, двумя строками чисел и решением.

## R6. Уровень размышлений: проверить по фактическому запросу

**Ничего не меняет. После R4, если строка T14 выкачена.**

Исходники показывают, как Hermes строит параметры запроса, но не что отправила установленная копия. На одном запросе агента убедиться, что серверу уходит `reasoning_effort: xhigh`: либо запустить на другом порту `llama-server --verbose` и направить туда один запрос Hermes, либо включить хук `pre_api_request`, который получает тело запроса. Записать дословно поле из запроса. Если поля нет или значение другое — записать и вернуть вопрос в первую часть; на сервере ничего не чинить.

## R7. Метки в деревьях задач

**Меняет метки. После R4.**

После T04 зависимость считается выполненной только при `status: done` **и** `verify: passed`. Задачи, закрытые человеком вручную до этого, перестанут открывать зависимые. В каждом проекте: `status.sh` → раздел `labels that disagree`. Для задач, которые человек действительно принял сам: `tasks.py --root <дерево> set <задача> verify passed --as reviewer`. Для остальных — вернуть в `review`. Решение по каждой задаче принимает человек; агент список только показывает.

## R8. Эксперименты

**После R5–R7. По одному изменяемому фактору. Решает и запускает человек.**

Имеют смысл только теперь: до исправлений первой части улучшение числа `done` могло означать улучшение ложной отчётности. Общие условия: один закреплённый SHA Hermes, один файл модели, явно заданный уровень размышлений, одинаковая политика холодного и тёплого кэша в обоих плечах, не меньше трёх повторов на плечо.

| Что сравнивается | Что смотреть |
| --- | --- |
| уровень `xhigh` против `medium` | вердикты, возвраты, вызовы ревьюера на принятую задачу; смена уровня меняет системное сообщение, поэтому оба плеча — с холодного кэша |
| `--reasoning-budget 8192` против без потолка | обрывает ли потолок полезное размышление; `finish_reason: length` |
| MTP выключен / включён / соседняя глубина черновика | полное время задачи, а не только tok/s; доля принятых черновиков |
| абсолютный порог сжатия `compression.threshold_tokens` | число сжатий, потеря деталей задания, время |
| Hermes `784d5c3f` против одного более нового закреплённого SHA | только с явным уровнем в обоих плечах и сверкой фактического запроса (R6) |

Метрики под подпиской: вызовы, ходы и токены ревьюера на корректно принятую задачу (из `calls.tsv`), события исчерпания лимита, простой очереди. Расчётный USD из ответа CLI — не списание.
