Но вывод review-v2 «по существу разногласий не осталось» преждевременен. В исправленных формулировках и предлагаемых решениях остались существенные проблемы:

## 2. Где агент прав

### 2.1. Я неточно процитировал «единственный найденный путь»

В первой версии ревью действительно было слово **«найденный»**. В своей проверке я привёл более сильную формулировку без этого слова и возразил против обещания полноты анализа, которого автор не давал.

Это неверное возражение с моей стороны. Утверждение «единственный найденный путь» не означает «других путей не существует». Предыдущий файл оставлен без изменений для сохранения истории; данное замечание к нему следует считать исправлением.

При этом N1 и N7 нужно различать. N1 повторяет вызовы внутри одного запуска `review.sh`. N7 завершает этот запуск с ошибкой; повторные обращения возникают, **если внешний процесс перезапускает reviewer**. В опыте три ручных старта дали три неучтённых вызова; сам один старт после аварии новых обращений не выполнял. Внешний бесконечный restart в реальной установке не установлен. Это условный риск повторений, а не второй встроенный бесконечный цикл.

### 2.2. N8 — реальный дополнительный случай ложной приёмки

В подставном ответе Claude использован объект:

```json
{
  "structured_output": {
    "verdict": "passed",
    "summary": "s",
    "evidence": "I read everything",
    "unmet": []
  }
}
```

Настоящий `review.sh` завершился с exit 0, задача получила `status: done` и `verify: passed`. Созданный `REVIEW.md` содержит заголовок Evidence без записей под ним.

Причина в [verdict.py](../verdict.py): строка truthy и проходит проверку непустоты evidence; последующий цикл перебирает символы и пропускает их как не-объекты. Валидатор не связывает отсутствие оформленных доказательств с пригодностью результата.

Это новая полезная конкретизация класса F4, а не повод спорить о нумерации. В собственную валидацию нужно включить контейнер evidence, каждый элемент и типы его полей. Как и для N1, опыт моделирует нарушение внешней схемы; он не доказывает, что настоящий CLI обычно возвращает такой ответ.

### 2.3. Прочие принятые уточнения

Согласен с разграничением worktree и границы записи; с порядком «определить исполняемую установку → исправить → развернуть проверенный набор»; с условной формулировкой N3; с сохранением уже сообщённого серверного SHA как исходной версии; с метриками подписки вместо объявления расчётного USD реальным списанием.

Дополнение про host prompt cache llama.cpp также уместно: на закреплённой сборке README действительно описывает `--cache-ram` с default 8192 MiB. Следовательно, чужой запрос в единственный slot не доказывает необратимую потерю сохранённого состояния. Фактическое восстановление нужно наблюдать. Источник: [параметры закреплённого сервера](https://github.com/ggml-org/llama.cpp/blob/5b59b83f4e2101ea173d4f853a0522d9971f48c6/tools/server/README.md).

## 3. B5: объект верхнего уровня не гарантирует корректный разбор

В review-v2, §1.1, B5 возражение принято лишь частично: автор утверждает, что прежний вывод верен для любого конверта-объекта. Это неверно. Объект может содержать поля неверных типов на любой глубине.

Два независимых входа, оба с **объектом** верхнего уровня и exit CLI 1:

```json
{"is_error":true,"structured_output":{"verdict":"passed","summary":42,"evidence":[{"claim":"x"}],"unmet":[]}}
```

```json
{"is_error":true,"permission_denials":[{"tool_input":42}],"structured_output":{"verdict":"passed","summary":"s","evidence":[{"claim":"x"}],"unmet":[]}}
```

Результаты настоящего reviewer:

| Вход | Исключение | Результат контроллера |
| --- | --- | --- |
| `summary: 42` | `AttributeError: 'int' object has no attribute 'strip'`, `verdict.py:37` | exit 1; задача остаётся review; ledger пуст |
| `tool_input: 42` | `AttributeError: 'int' object has no attribute 'get'`, `verdict.py:27` | exit 1; задача остаётся review; ledger пуст |

`is_error=true` не спасает: добавление причины в `why` не прекращает небезопасный разбор и рендер остальных полей. Это одновременно подтверждение N7 и прямое опровержение исправленной формулировки B5.

Корректно написать: «Для корректно типизированного конверта этот отказ проходит по ветке unusable; повреждённые типы, в том числе вложенные, могут прервать обработку исключением».

Граница надёжности должна быть двойной: парсер отвергает неверную структуру, а контроллер сохраняет факт вызова и при ненулевом завершении самого парсера. Только первая мера не защищает учёт от ошибок записи на диск, последующей регрессии парсера и других исключений.

## 4. T03 ошибочно выводит причину сбоя по успеху следующей задачи

### 4.1. Ошибка в самом правиле

Review-v2 принимает правило из T03: если A несколько раз упала, а B затем получила ответ, значит причина — задача A, и A нужно заблокировать.

Из этих наблюдений такой вывод не следует. Одновременно изменились **задача и время**. Сервис мог восстановиться, лимит — сброситься, авторизация — обновиться, а запросы могли попасть на разные backend-узлы. Возможны как общая временная причина, так и особенность A. Одного ответа B недостаточно, чтобы выбрать между ними.

Верно и обратное: два сбоя по разным задачам не доказывают общий outage. Обе задачи могут иметь слишком большие запросы или использовать одинаково неподходящий режим. Наблюдение полезно для выбора дальнейших действий, но не является достоверной классификацией причины.

### 4.2. Воспроизведение именно предложенного решения

В отдельную временную копию харнесса перенесены инфраструктурные фрагменты T03: `INFRA_MAX`, skip-list, ветка infra, suspect-task и выход при отсутствии следующей задачи. В `verdict.py` временной копии добавлен приведённый в T03 predicate. Другие задачи плана не реализовывались; все ответы в этом опыте — обычные корректно типизированные объекты, поэтому приведение типов из T02 для сценария не требуется.

Подставной Claude моделирует общий временный сбой, **не анализируя содержимое prompt**:

```text
вызовы 1–3: exit 1, is_error=true, result="temporary outage"
вызовы 4 и далее: корректный passed
```

В очереди две задачи, A и B; `HH_REVIEW_INFRA_MAX=3`. Три последовательных запуска reviewer дали:

| Запуск | Что произошло | Exit |
| --- | --- | ---: |
| 1 | A получает временную ошибку; счётчик 1 | 75 |
| 2 | A получает временную ошибку; счётчик 2 | 75 |
| 3 | A получает третью ошибку; B после восстановления получает passed; A блокируется | 0 |

В логе появилась причина:

```text
the reviewer fails on this task while it works on others
```

Причина ложная: stub отказал первым трём вызовам независимо от задачи. После возвращения A в review **та же A с тем же содержимым** сразу получила passed. Код T03 превратил восстановившийся общий сбой в блокировку исправной задачи.

Это контрпример к новому алгоритму. Он не означает, что данный алгоритм уже установлен в текущем `review.sh`: производственный код в ходе проверки не изменялся.

### 4.3. Как исправить решение

Разделить состояние задачи и состояние сервиса. Сбой транспорта или лимит не является verdict по задаче. После исчерпания допустимых попыток можно отложить A, установить время следующей попытки и дать очередь другим задачам, сохранив честную причину «ревью не состоялось».

Ответ B может разрешать ограниченный повтор A после восстановления. Если A продолжает падать, допустима отдельная эскалация для человека, но причина должна описывать наблюдение — «повторные сбои вызова для A», а не недоказанный вывод о содержимом задачи. Прямой структурированный отказ вроде превышения длины запроса даёт больше оснований для классификации, чем успех другой задачи.

Для конечности нужны независимые ограничения попыток, задержек и использования ресурса. Необязательно автоматически блокировать A после успеха B, чтобы избежать голодания очереди. Для минимальной первой правки проще записать инфраструктурный отказ, сохранить review и выйти 75; более сложное планирование повторов можно реализовать отдельно.

Обязательный новый сценарий приёмки: «три общих временных ошибки → восстановление → ответ B → A не объявлена неисправной и может продолжить ревью».

### 4.4. `error_max_*` — не доказательство свойства задачи

В T03 все subtypes с этим префиксом объявлены свойством конкретной задачи. Исчерпание бюджета/числа ходов действительно надо ограничивать и фиксировать, но оно может зависеть от слишком малого общего лимита, поведения модели или настроек CLI. Это результат попытки при заданных ограничениях, а не самостоятельное доказательство дефекта кода.

Разумно различать известные документированные причины, не делать смысловой вывод по открытому строковому префиксу и оставлять неизвестные варианты явно неизвестными. Фактический limit-envelope установленного Claude по-прежнему не получен.

## 5. Новый T03 искажает учёт использования

В шаге 8 T03 предложено считать reviewer calls как число строк ledger с `actor=reviewer`. Но новая ветка suspect-task пишет дополнительную строку о блокировке A **без обращения к Claude**.

В опыте из §4 получено:

```text
фактических вызовов stub Claude: 4
строк ledger с actor=reviewer:   5
```

Три строки — ошибки A, одна — блокировка A по ответу B, одна — приёмка B. Такая метрика смешивает вызовы и переходы состояния. Это особенно существенно после правильного решения оценивать использование подписки по вызовам и токенам.

Есть и потеря известных данных. В ошибочные ответы опыта специально включено `total_cost_usd: 0.1`. Infra-ветка расположена до чтения этого поля и записала строку ledger без стоимости. Поле подставное, реальных расходов не было; опыт показывает, что доступная оценка теряется. Сбой после частично выполненной работы нельзя автоматически приравнивать к нулевому использованию.

Нужен отдельный идентификатор вызова и ровно одна запись его результата: exit, raw envelope, время, доступные usage/cost, причина завершения. События изменения статуса могут ссылаться на вызов, но не увеличивать число вызовов. Если usage неизвестен, это неизвестное значение, а не ноль. Факт вызова должен сохраняться до разбора verdict либо гарантированно фиксироваться независимо от успешности этого разбора.

## 6. T02: неверные типы нельзя молча превращать в пригодное ревью

Направление T02 правильное: сначала проверить типы, затем смысл. Но приведённые правила не полностью обеспечивают заявленный результат.

### 6.1. Потеря неверно оформленного unmet

Таблица T02 предлагает отбрасывать нестроковые элементы списка `unmet`, не добавляя причину непригодности за каждый такой элемент. Например:

```json
{"verdict":"passed","summary":"s","evidence":[{"claim":"read source"}],"unmet":[42]}
```

После буквально предложенной нормализации `[42]` превращается в `[]`. Тип контейнера становится правильным, противоречия с passed больше не видно. Передача нормализованного ответа текущему валидатору дала `passed 0 yes`; дополнительные смысловые правила T02 для такого нормализованного объекта тоже не дают причины отказа.

Это проверка предлагаемого правила нормализации, не утверждение о готовой реализации T02. Исполнитель может сам добавить недостающую проверку, но задача не должна полагаться на его догадку.

Нормализация допустима для безопасного отображения ошибки. Решение о пригодности должно помнить, что исходный объект нарушал контракт. Иначе некорректное свидетельство исчезает и превращается в основание для приёмки.

### 6.2. Не охвачены вложенные поля

Review-v2 перечисляет `evidence` как список объектов, но этого недостаточно. Требуются типы `claim`, а также `command` и `output`, если они присутствуют. Для permission denial недостаточно объекта: его `tool_input` тоже может быть числом, как показано в §3.

Дополнительно на текущем коде воспроизведено: `evidence=[{"claim":42}]` проходит до done/passed. Это не авария, поскольку renderer превращает claim в строку; такой результат всё равно нарушает переданную CLI-схему.

В T02 также указано место вставки «между строками 18 и 35», хотя обращения `envelope.get` и `out.get` уже происходят на строках 12–16. Проверки верхнего уровня должны стоять **до первого обращения к его полям**. Позднее указание «сначала типы» правильно по смыслу, но границы SCOPE стоит согласовать с ним.

Фраза «не падает ни на каком входе» слишком абсолютна. Реалистичный контракт: любые JSON-значения и повреждённый JSON дают контролируемый protocol error; проблемы чтения/записи/окружения перехватывает контроллер с сохранением попытки. Перехватить ошибку и превратить её в passed недопустимо.

Минимальное дополнение к приёмке T02: неправильный верхний тип, неправильный structured_output, отсутствующее обязательное поле, неправильный тип элемента unmet, неправильный claim, неправильный command/output и неправильный вложенный tool_input. Во всех случаях исключена ложная приёмка и сохранена диагностическая причина.

## 7. «Сейчас сервер работает в xhigh» пока не установлено

Review-v2 правильно достраивает цепочку: новый custom profile Hermes может сформировать `reasoning_effort: medium`, а `llama-server` передаёт поле запроса в Jinja. В официальном шаблоне medium не добавляет инструкцию xhigh/low в system prompt. Всё это подтверждается исходниками.

Но вывод «сейчас на сервере действует xhigh, обновление обязательно переведёт в medium» сильнее сведений об установке. Сам review-v2 перечисляет как неизвестные слитую конфигурацию, команду сервера и фактический шаблон. Отсутствие effort в YAML репозитория не исключает пользовательский/per-model override, CLI-аргумент или серверный template override.

В новой функции Hermes есть условия: Chat Completions, default у provider profile, проверка capability reasoning и отдельные исключения. Не следует превращать условное изменение default конкретного SHA в гарантию поведения любого `hermes update`. Источники: [новая политика Hermes](https://github.com/NousResearch/hermes-agent/blob/6182078cb754f0d17ce83ade09d60e1250add111/agent/reasoning_params.py), [передача параметра в llama.cpp](https://github.com/ggml-org/llama.cpp/blob/5b59b83f4e2101ea173d4f853a0522d9971f48c6/tools/server/server-common.cpp).

Корректная формулировка: «При незаданном effort, стандартном custom Chat Completions и официальном шаблоне переход с сообщённого серверного SHA на исследованный `6182078` может заменить server-default xhigh явным medium; перед сравнением необходимо зафиксировать фактический запрос».

### 7.1. Снята одна неопределённость review-v2: старый SHA принимает xhigh

Автор отдельно оставил непроверенным, понимает ли `784d5c3f` явный `agent.reasoning_effort: xhigh`. Проверены и исполнены оригинальные функции `resolve_reasoning_config`, `clamp_effort` и метод custom profile этого SHA:

| Настройка | Разрешённая конфигурация | Верхнеуровневое API-поле |
| --- | --- | --- |
| Не задана | `None` | Поле отсутствует |
| `xhigh` | `{enabled: true, effort: xhigh}` | `reasoning_effort: xhigh` |
| `medium` | `{enabled: true, effort: medium}` | `reasoning_effort: medium` |
| `high` | `{enabled: true, effort: high}` | `reasoning_effort: high` |

Последняя строка не означает совместимость с Qwen-шаблоном: Hermes допускает значение, которое официальный Qwen3.8-шаблон отвергает. Источники: [resolver старого SHA](https://github.com/NousResearch/hermes-agent/blob/784d5c3f9c2cb77698d8a9d2e72b1d106a38ea88/hermes_constants.py), [custom profile](https://github.com/NousResearch/hermes-agent/blob/784d5c3f9c2cb77698d8a9d2e72b1d106a38ea88/plugins/model-providers/custom/__init__.py), [допустимые wire-значения](https://github.com/NousResearch/hermes-agent/blob/784d5c3f9c2cb77698d8a9d2e72b1d106a38ea88/agent/reasoning_effort.py).

Это проверка построения параметров по исходникам, не полный сетевой запуск установленного Hermes. Её достаточно, чтобы убрать предположение, будто явный xhigh принципиально недоступен на старой версии; фактический запрос всё равно следует наблюдать.

### 7.2. Смена effort не равна буквальному уничтожению всего кэша

При рендере одного официального шаблона с одинаковой историей и разными effort получился общий строковый префикс `<|im_start|>system\n`. Различие начинается рано, поэтому повторная обработка может затронуть почти весь prompt. Но «сбрасывает весь префиксный кэш» — неточная универсальная формулировка: рендер строк не измеряет токенизацию, host cache и восстановление серверного состояния.

Практическая рекомендация автора верна: сравнивать оба плеча с одинаковой политикой cold/warm cache. Для неё не требуется обещать полное обнуление. Источник шаблона: [закреплённый Jinja Qwen](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/chat_template.jinja).

## 8. Про адаптацию релиза: возражение полезно, но не является опровержением

Автор прав: если одному Hermes дать один контроллер, другому — другой, различие результатов нельзя приписывать только модели/версии. Именно поэтому предыдущий отчёт рекомендовал для неизменного харнесса два совместимых SHA.

Неверно лишь утверждение, что **любая** адаптация формата обязательно требует двух разных контроллеров. Можно использовать один контроллер с двумя совместимыми transport adapters, которые нормализуют запуск, session ID и завершение в единый контракт. Это обычное проектное решение, но эквивалентность поведения адаптеров должна быть проверена, а влияние адаптации — явно учтено в дизайне эксперимента.

У меня не было доказательства эквивалентности таких ещё не написанных адаптеров, и фразу «эксперимент возможен после адаптации» нельзя читать как обещание уже обеспеченной чистоты сравнения. В этом ограничении возражение агента принимается. Практического разногласия по текущему плану нет: не писать адаптер ради сравнения с тегом, а использовать два совместимых закреплённых SHA.

## 9. Первая партия пока не даёт обещанной безопасности очереди

Review-v2 сохраняет первую партию T00–T07, а `fix-tasks.md:47` прямо называет ночной прогон после неё безопасным. Это слишком широкое обещание.

T07 исправляет момент публикации review относительно коммита. Она не меняет каталог, в котором запускаются check и Claude. T05 исправляет идентификацию измеряемого дерева, но тоже не заставляет reviewer измерять именно сохранённый commit. Эта работа явно отнесена к T08.

Поэтому после описанной первой партии остаётся допустимая последовательность:

1. A записывает commit A и передаётся на ревью.
2. Worker выполняет B и меняет/коммитит общее дерево.
3. Reviewer A показывает diff сохранённого commit A.
4. Check и чтение файлов идут в текущем дереве B.

Fingerprint может правильно описывать B; это не делает его свидетельством для A. Отсутствие одновременного запуска двух процессов тоже не помогает, если дерево уже успело измениться. Сам механизм ранее воспроизведён как F3; здесь проверено, что предлагаемые T00–T07 его не устраняют по своим границам изменения. Все семь задач во временной реализации не выполнялись.

Исправить план можно двумя способами: включить T08 и нужные ограничения T09 до обычного ночного ревью очереди либо явно ограничить ранний запуск режимом, где после каждой задачи фиксируется результат, reviewer проверяет его до любых последующих изменений, а прочие процессы не меняют копию. Наличие `HH_REVIEW_ONLY` само по себе не доказывает, что выбран правильный код.

Это не требование немедленно реализовать всю систему изоляции. Это требование не обещать корректность общей очереди до закрытия уже известного пути приёмки не того снимка.

## 10. T11: широкое разрешение `git diff` не является обязательным

Убирать `Bash(sed -n:*)` разумно; автор корректно сохраняет оговорку, что фактический permission engine не испытывался. Но фраза в T11 «убрать `Bash(git diff:*)` нельзя — ревьюеру нужен диф» неверна как обоснование.

Контроллер уже формирует `.under-review.diff`. Ревьюеру можно дать этот файл для Read; можно разрешить конкретные формы команды или вынести подготовку diff в контролируемый инструмент. Необходимость читать diff не требует разрешать все опции `git diff`.

Также правило `Bash($TEST_CMD *)` разрешает суффикс аргументов, а не семантическое действие «сузить выбор тестов». В зависимости от команды дополнительные аргументы могут менять конфигурацию, загружать плагины, выбирать выходные пути и режимы. Официальная документация описывает именно matching команды, не верификацию смысла всех её опций. Источник: [Claude Code permissions](https://code.claude.com/docs/en/permissions).

Это не опровержение полезности T11: она существенно сужает разрешение по сравнению с любым `python3`. Но её результат должен так и называться — сужение разрешений. Если задача требует дополнительных выборочных тестов, нужен определённый набор поддерживаемых аргументов или контролируемый test runner. Гарантию невозможности записи дают права среды, как автор теперь правильно признаёт.
