### 1.3. Reasoning в истории: штатный режим модели, а не опция для эксперимента

**Утверждение отчёта** (§4.1): Hermes вырезает `reasoning_content` при `reasoning_echo: false`; Qwen «рекомендует сохранять reasoning»; предлагается эксперимент E1, «прирост заранее не обещается».

Фактическая часть подтверждена полностью:

- `hermes_cli/config_defaults.py:250` — `"reasoning_echo": False`, комментарий над ним: custom-провайдеры автоматически не распознаются.
- `agent/message_sanitization.py:513–522` — при `needs_thinking_pad == False`: `api_msg.pop("reasoning_content", None)`. Уточнение к отчёту: функция живёт в `message_sanitization.py`, а не в `reasoning_params.py`; в последнем — только чтение флага (`:142–152`).
- В сохранённой сессии размышление остаётся: `agent/chat_completion_helpers.py:1494–1539` пишет и `reasoning`, и `reasoning_content` при создании сообщения. То есть включение echo подействует и на resume старых сессий.
- llama.cpp принимает поле на входе и отдаёт шаблону: `common/chat.cpp:453–454`, `:233–234`.

Спор — в оценке веса. Отчёт не открывал шаблон модели, а он решает дело. Официальный `chat_template.jinja` (`Qwen/Qwen3.8-27B`, строки 111–117):

```jinja
{%- set reasoning_content = '' %}
{%- if message.reasoning_content is string %}{%- set reasoning_content = message.reasoning_content %}{%- endif %}
...
{%- if preserve_thinking is undefined or preserve_thinking is true or loop.index0 > ns.last_query_index %}
    {{- '<|im_start|>' + message.role + '\n<think>\n' + reasoning_content + '\n</think>\n\n' + content }}
```

`preserve_thinking` по умолчанию включён (карточка: «`preserve_thinking` is enabled by default for all workloads»; «especially beneficial for agent scenarios where decision consistency and reduced redundant reasoning are critical. It also improves KV cache utilization»). Значит, сейчас:

- каждый прошлый ход ассистента рендерится как `<think>\n\n</think>` — пустой блок, которого модель не порождала. Модель видит историю, где она якобы действовала не думая. Это режим, в котором её не мерили;
- отрендеренный prompt хода N расходится с тем, что сервер держит в кэше после хода N−1 (там блок с мыслями), ровно в начале предыдущего ответа. Для гибридной модели (DeltaNet) откат состояния возможен только до контрольной точки, отсюда зависимость от `--ctx-checkpoints`, которую `model-serving.md` описывает как данность.

Поэтому формулировка должна быть обратной: `model.reasoning_echo: true` — возврат к штатному режиму производителя, и доказывать надо пользу от `false`, а не от `true`. E1 стоит первым среди экспериментов этапа F, а не наравне с MTP и глубиной черновика.

Честная цена, которую отчёт тоже не называет: при бюджете 8192 токена на ход сохранённые мысли ускоряют рост контекста, и сжатие на 98 304 наступит раньше. Это и есть то, что E1 должен измерить (число компрессий на задачу, не только tok/s).

Не проверено: совпадает ли шаблон, зашитый в GGUF от Unsloth, с официальным. Unsloth шаблоны иногда правит. Проверяется одним запросом `/props` (поле `chat_template`) на сервере.

**Поправка к E2.** `reasoning_effort` в шаблоне — это инструкция в системном сообщении (строки 46–56), и шаблон бросает исключение на всё, кроме `xhigh|medium|low`. При этом `llama-server --reasoning-effort` принимает ещё `minimal`, `high`, `max` (`tools/server/README.md:234`). Значение `high` даст ошибку рендера, а не «чуть меньше xhigh». Смена уровня меняет системный prompt, то есть сбрасывает весь префиксный кэш — сравнивать E2 надо на холодном кэше в обоих плечах.

### 1.5. Экономика: ревьюер работает по подписке, а отчёт считает доллары

**Утверждение отчёта** (§1, приоритет 3; §8.3, «Оплаченная стоимость: USD…»; основная метрика «Расход Claude на принятую задачу = все оплаченные расходы серии / число принятых задач»).

`claude -p` в этой установке запускается под подпиской, токены API не оплачиваются. Поле `total_cost_usd` в ответе CLI остаётся, но это расчётная величина по прайсу API, а не списание. Следствия:

- Настоящий расходуемый ресурс — лимит использования подписки (окна, после которых CLI отвечает ошибкой до сброса). Он тратится числом и размером вызовов, а не долларами. Метрика отчёта должна звучать так: вызовов ревьюера, ходов и токенов на корректно принятую задачу, плюс число упираний в лимит и часы простоя очереди из-за них. `total_cost_usd` годится как относительная мера «тяжести» одного ревью, не как стоимость.
- `--max-budget-usd 5` в `review.sh:298` ограничивает одно ревью по той же расчётной величине. Работает ли этот потолок под подпиской так же, как под API-ключом, я не проверял; это надо увидеть на одном реальном вызове (поле `total_cost_usd` и причина остановки в конверте).
- `status.sh` суммирует доллары из `ledger.tsv`. Под подпиской эта сумма ничего не говорит о том, сколько ревью ещё можно сделать сегодня.
- Экономическая цель проекта от этого не меняется, меняется её единица: беречь надо не деньги на вызов, а число вызовов до упора в лимит. Поэтому дешёвые детерминированные отсевы до ревьюера (pregate, готовность пакета из F7) становятся важнее, а не менее важными: каждый пустой вызов отнимает место у настоящего ревью.
- Исчерпание лимита из редкой «ошибки API» превращается в штатное ежедневное событие, и харнесс обязан его переживать. Сейчас не переживает — см. N6.

## 2. Чего в отчёте нет

### N1 — P0. Вердикт вне перечисления: бесконечный цикл ревью (воспроизведено)

`verdict.py` не проверяет значение `verdict`; `review.sh:341–369` — `case` без ветки по умолчанию. Ответ с `verdict: "banana"` даёт `usable: yes`, `review.sh:340` стирает счётчик раундов, ни одна ветка не срабатывает, задача остаётся в `review`, и в режиме очереди `tasks queue review | head -n 1` отдаёт её же снова. Прогон с подставным `claude`, ограниченный `HH_REVIEW_MAX=3`:

```text
== 10-a-01-x (review round 1/2)   verdict: banana (usable: yes)   cost: 1.50 USD
== 10-a-01-x (review round 1/2)   verdict: banana (usable: yes)   cost: 1.50 USD
== 10-a-01-x (review round 1/2)   verdict: banana (usable: yes)   cost: 1.50 USD
reviewed: 3, settled: 0
```

Счётчик стоит на «1/2», в `ledger.tsv` ничего не пишется, расход не виден `status.sh`. По умолчанию `HH_REVIEW_MAX=0`, то есть цикл ничем не ограничен. Под подпиской (§1.5) он не тратит деньги, а выжигает лимит использования до упора, после чего N6 блокирует остальную очередь. Сумма «1.50 USD» в выводе — число из подставного ответа, не списание. Сейчас от этого защищает одна лишь `--json-schema` на стороне CLI. Отчёт упоминает «неизвестный verdict» в приёмке F4, но не это последствие. Лечится тем же исправлением F4 плюс ветка `*)` в `case`, переводящая в негодное ревью.

### N2 — P0. `done` не требует `verify: passed`, и зависимые задачи открываются (воспроизведено)

`tasks.py:57–65` (`depends_met`) смотрит только `status == done`. `tasks.py:10`: роль `agent` вправе писать `status` с любым значением. Проверка:

```text
       P1 done   a   (status is done)      # verify: pending
ready  P1 todo   b                         # depends: a
$ tasks.py set <b> status done             # роль по умолчанию — agent
rc=0
```

README утверждает обратное: «a forged `status: done` changes nothing except the moment someone notices». Меняет: задача уходит из обеих очередей (её никто не отревьюит), а всё, что от неё зависит, запускается поверх непроверенного кода. `status.sh` расхождение `done` без `verify: passed` не показывает. Отчёт в F5 отмечает саму возможность записи, в §6.3 даёт условия `done`, но не называет дыру в `depends_met`. Исправление дешёвое и не ждёт изоляции: готовность зависимости = `status: done` **и** `verify: passed`; `status: done` исключить из значений, доступных роли `agent`; `status.sh` — строка о несогласованных метках.

### N3 — P1. При `HH_COMMIT=1` (значение по умолчанию) замер не переиспользуется никогда (воспроизведено)

`run.sh:294` вызывает `measure` до коммита (`:315–318`). Оттиск записывается с грязного дерева, ревью считает его с чистого:

```text
dirty    8682c651…   <- что пишет measure() до коммита
clean@B  da39a3ee…   <- что считает review.sh после HH_COMMIT=1
```

Несовпадение гарантировано, проверка проекта гонится второй раз. Обещанные README «nine minutes … now spends none» выполняются только при `HH_COMMIT=0`. Отчёт видит этот сценарий как риск будущего исправления («замер до коммита и тот же код после коммита тогда будут считаться разными»), но не как действующий дефект. Вместе с F1 получается худшее из двух: кэш промахивается там, где должен попадать (первое ревью), и попадает там, где не должен (чистый HEAD после чужого коммита). Идентификатор содержимого снимка из F1 закрывает оба.

### N4 — P1. Зависимость от `main` Hermes нигде не зафиксирована

См. §1.1. Отдельный пункт, потому что это дефект харнесса, а не только отчёта: ни версия, ни SHA, ни наличие `--format` не проверяются, а README называет не ту версию.

### N5 — P2. Разрешения ревьюера: кроме `python3:*` есть ещё две записи с побочной записью

К F6. Не проверено запуском (нужен реальный вызов Claude Code), поэтому как гипотеза: `Bash(sed -n:*)` допускает `sed -n 'w <файл>' <вход>`, а `Bash(git diff:*)` — `git diff --output=<файл>`. Оба пишут файл, оба начинаются с разрешённого префикса. Документация Claude Code прямо предупреждает, что правила, ограничивающие аргументы, хрупкие. При переходе на read-only-снимок (исправление F6) вопрос снимается сам.

### N6 — P1. Упор в лимит подписки блокирует всю очередь ревью за секунды (воспроизведено)

`verdict.py:19` считает негодным любое ревью с ненулевым выходом или `is_error`. `review.sh:319–337` на негодное ревью увеличивает счётчик и делает `continue`; очередь тут же отдаёт ту же задачу, второй отказ — `blocked` (`HH_REVIEW_MAX_ROUNDS=2`), затем следующая задача. Паузы нет, причина отказа не различается. Прогон с подставным `claude`, который отвечает ошибкой лимита, три задачи в `review`:

```text
== 10-01-a (review round 1/2)   the review could not be relied on
== 10-01-a (review round 2/2)   2 unusable review(s) -> blocked, a human has to look
== 10-02-b (review round 1/2) … (review round 2/2) -> blocked
== 10-03-c (review round 1/2) … (review round 2/2) -> blocked
reviewed: 6, settled: 0          seconds: 2
```

Все три задачи в `blocked` за две секунды, в `ledger.tsv` — «2 unusable reviews», как будто ревьюер дважды не смог оценить работу. Утром это неотличимо от настоящих блокировок, и каждую надо возвращать руками. Оговорка: точный вид ответа CLI при исчерпании лимита я не видел (подставной ответ — `is_error: true`, exit 1); путь в коде одинаков для любого ненулевого выхода и любого `is_error`, так что вывод от формы сообщения не зависит.

Отчёт в этапе E говорит общее «отличать ошибку кода, инфраструктурный сбой и непригодный ответ ревьюера». Под подпиской это не улучшение учёта, а условие ночной работы. Нужное поведение: сбой вызова (ненулевой выход, `is_error`, нет `structured_output`) не трогает счётчик раундов и не меняет статус; петля останавливается или ждёт с растущей паузой; в `ledger.tsv` пишется отдельная причина. Счётчик негодных ревью — только для ответов, которые пришли и оказались непригодны по содержанию.
